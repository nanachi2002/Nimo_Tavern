Privacy & security

NimoTavern is built so that the server can't read your data, not just promises not to. Here's exactly how it works, and where its limits are.

What the server stores

  • Your username, and when the account was created.
  • Salts and a hash of your login proof. The login proof is derived from your password in your browser (Argon2id, 64 MiB). The server hashes it again (scrypt). Your password itself is never sent.
  • Your data key, encrypted twice: once with a key derived from your password, once with a key derived from your recovery phrase. Neither of those keys ever reaches the server.
  • Encrypted blobs: each file (chat, character, setting, API keys…) is compressed and encrypted with AES-256-GCM. Blobs are named with an HMAC, so even file names and folder structure are hidden. We can see how many blobs you have and their sizes.
  • Session tokens, stored hashed. They expire after 30 days.

What the server never stores

  • No email, real name, phone number or payment info.
  • No IP addresses or user agents in the database. The app doesn't write access logs. IPs are only held in memory, as keyed hashes, for rate limiting (a few minutes) and for counting unique visitors per day (the random salt is discarded each day).
  • Anonymous usage counts for the operator: per day, how many page views, sign-ups and logins happened, how many unique visitors there were, and how many accounts were active that day, week or month. These are plain numbers: nothing is stored per user, per IP or per page visited, and the sets used to avoid double-counting only exist for the current period and are then deleted.
  • No third-party analytics, trackers, ads or third-party scripts. The only exception is the Cloudflare Turnstile captcha on the sign-up page, if it's enabled.

Where SillyTavern runs

Normally SillyTavern has a server that reads and writes your files and forwards your prompts and API keys to the AI provider. In NimoTavern that server code runs inside your browser, in a Service Worker, on top of an encrypted virtual file system. When you chat, your browser sends the request directly to the provider you set up (OpenRouter, OpenAI, Anthropic, Google, DeepSeek, Mistral, your own KoboldCpp…).

Optional relay: some providers refuse requests coming from browsers. For those, you can turn on a relay in your account settings. It's off by default. With it on, the request passes through this server's memory without being logged or stored, but you have to trust the server for that request.

Honest limitations

  • You trust the code you're served. Like any web app, including web-based password managers, a malicious server operator could change the JavaScript to steal keys. NimoTavern is open source (AGPL-3.0) so the code can be audited. If you need zero trust, run SillyTavern locally.
  • Your AI provider sees your prompts. Encryption protects your data at rest and from NimoTavern. The provider you send prompts to can still read them. Pick one whose policy you trust, or run a local model.
  • Your device holds the keys while you're logged in. They're stored as non-exportable keys in your browser. Log out on shared computers: that wipes the keys and the local encrypted cache.
  • Lost password + lost recovery phrase = lost data. There's no reset. That's the price of real end-to-end encryption.
  • Features that need server-side AI models are disabled (vector storage, server-side image captioning and classification), because they would require plaintext on the server. SillyTavern server plugins (Node.js code) never run on our server; authors can port them to NimoFramework, which runs them in your browser.
  • Third-party extensions run in your browser, with your access. An extension you install can read and change your own tavern, so only install ones you trust. Your browser downloads them straight from GitHub; we don't see which ones you install. They can't reach other users or our server, and they never run on the multiplayer site.
  • Logging out wipes this site's browser storage (caches, local databases, any background scripts), so nothing carries over to the next person on a shared computer.
  • Metadata: the server can see when you're active, how much you store and when blobs change, but not what they contain.

Multiplayer sessions

Multiplayer works differently from solo chats, and it is not end-to-end encrypted. To run the AI for a group, even when the host is offline, the server has to build the prompt itself. While it does, it reads the session: the character, the world setting, the lorebook, every player's messages and persona (name, picture, description), and the host's multiplayer API key.

  • Encrypted at rest. Each session has its own random key, wrapped with a server key. Everything with content (settings, messages, personas, pictures, the API key) is stored encrypted with AES-256-GCM. A database dump or backup alone reveals nothing.
  • Never logged. Prompts, replies and keys are only in memory while the AI writes. Errors show the host only the provider's status.
  • Deleted for good when the host ends the session, when the host's account is deleted, or after 90 days without activity.
  • What the server can see in plain form: who is in which session and who invited whom (usernames), the turn order and round number. Never the content of your solo chats.
  • Players only see what's on screen. The character definition, world setting, lorebook and API key stay with the host and are never sent to players.
  • Use a separate API key for multiplayer. Your solo key never leaves your browser; the multiplayer key has to be stored on the server for the session to run. Set a spending limit on it with your provider.
  • Multiplayer has its own site, play.nimorp.lol, with its own login. To the browser it's a separate website, so extensions installed on the main site can't load there or reach your sessions. The play site never writes to your synced storage: session chats stay in that browser only.
  • Invites are optional. You can turn invites off or block someone in your Account mailbox. Inviting an unknown or unreachable username always gives the same answer, so usernames can't be probed this way.

In short: the operator could technically read a multiplayer session while it runs. If that's not OK for a story, keep it solo.

Cryptography summary

  • Password → Argon2id (m=64 MiB, t=3, p=1, random 128-bit salt) → HKDF-SHA256 → key-encryption key + login proof
  • Recovery: 12-word BIP39 phrase (128-bit entropy) → HKDF-SHA256 → key-encryption key + recovery proof
  • Data key: random 256-bit, wrapped with AES-256-GCM
  • Files: deflate → AES-256-GCM (random 96-bit IV) with the blob ID as associated data, IDs = HMAC-SHA256(path)
  • Transport: HTTPS only, HSTS, strict Content-Security-Policy, HttpOnly session cookies
