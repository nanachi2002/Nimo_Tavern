NimoFramework lets a SillyTavern server plugin (the Node.js part some extensions need) run on NimoTavern. Your plugin keeps the same shape (info, init(router), exit()) and the same URLs (/api/plugins/<id>/…). The difference is where it runs: in the browser of the person who installed it, never on NimoTavern's server.

If you're a user and an extension you like needs a server plugin, send its author this page.

At a glance

1. Add one line to your extension's manifest.json: "nimo": { "framework": 1, "server": "server.cjs" }.

2. Put your plugin in server.cjs as one CommonJS file. Already one plain CommonJS file? Nothing to build. Otherwise, one esbuild command does it.

3. Commit, push, install from GitHub on NimoTavern. Your UI's fetch('/api/plugins/<id>/…') calls work unchanged.

Not sure your plugin can be ported? Paste it into the port check below.

The idea in 30 seconds

On regular SillyTavern your plugin runs in Node, on the machine that hosts SillyTavern. On NimoTavern, SillyTavern's own server code already runs inside each user's browser, in a Service Worker that decrypts their files locally. NimoFramework loads your plugin there, next to it. Your plugin can

Register routes, read the request, stream answers. Read and write the user's files (characters, chats, settings…). Store its own data. Call websites and AI providers the way the user's browser can.

Your plugin can't

Start programs, use native addons, open ports or raw sockets, run in the background on its own, or reach other users. It never runs on the multiplayer site.

Why not just run plugins on the server?

On your own PC, a server plugin is your business. NimoTavern's server is shared by everyone: a plugin there would run next to every other account, so one buggy or malicious plugin could read other people's data or take the site down. And NimoTavern can't read anyone's data by design, so it couldn't give a plugin your files anyway. That's why NimoTavern never runs anyone's code on its server, and this won't change. Running your plugin in the user's browser keeps all of that true.

Quick start (5 minutes)

Here's a complete, working extension with a backend. It is also in the NimoTavern repository: nimo/framework/example. You can install that URL directly to try it.

my-extension/ ├── manifest.json ← one extra line ├── index.js ← your UI, unchanged ├── style.css └── server.cjs ← your plugin, as one CommonJS file
  1. Declare the server file in manifest.json

    Regular SillyTavern ignores the nimo field, so the same manifest works everywhere.

    {
    "display_name": "My extension",
    "js": "index.js",
    "css": "style.css",
    "author": "You",
    "version": "1.0.0",
    "nimo": { "framework": 1, "server": "server.cjs" }
}
  2. Write server.cjs

    The same shape SillyTavern loads from its plugins/ folder. info.id becomes the URL: /api/plugins/my-plugin/.

    module.exports = {
    info: { id: 'my-plugin', name: 'My plugin', description: 'Says hello and counts.' },

    async init(router) {
        router.post('/probe', (req, res) => res.sendStatus(204));   // "is my backend there?"

        router.get('/hello', (req, res) => {
            res.json({ hello: nimo.user.name });
        });

        router.post('/count', (req, res) => {
            const count = nimo.storage.get('count', 0) + 1;
            nimo.storage.set('count', count);                       // encrypted and synced
            res.json({ count });
        });
    },

    async exit() {},
};
  3. Call it from your UI

    Exactly what you'd write for SillyTavern. Use SillyTavern's getRequestHeaders() as usual; it works on NimoTavern too.

    import { getRequestHeaders } from '../../../../script.js';

const API = '/api/plugins/my-plugin';
const r = await fetch(API + '/hello', { headers: getRequestHeaders() });
const { hello } = await r.json();
toastr.info(`The plugin says hello to ${hello}`);
  4. Push and install

    Commit everything, including server.cjs, and push to GitHub. On NimoTavern: Extensions → Install extension → paste https://github.com/you/my-extension. Your plugin starts on the first request to /api/plugins/.

Porting an existing plugin

Most plugins port with no code changes. What you need to do depends on how your plugin is written:

Your plugin is…What to do
One CommonJS file that only uses provided modulesNothing to build Copy it into your extension as server.cjs.
ES modules (import/export), several files, or npm packagesOne build command Bundle it with esbuild (below).
Uses child_process, native addons, sockets…Change those parts See limits: each has a browser-friendly replacement.

Bundling with esbuild

esbuild packs your files and their npm packages into one CommonJS file. Run it in your plugin's folder:

npx esbuild src/index.js --bundle --platform=node --format=cjs --external:express --external:node-fetch --outfile=server.cjs
  • --platform=node keeps Node built-ins (fs, path, node:crypto…) as require() calls. NimoFramework provides them.
  • --format=cjs turns export const info / export async function init into module.exports. NimoFramework finds them there (a default export works too).
  • --external:express --external:node-fetch uses the versions NimoFramework (and SillyTavern) already have, instead of bundling copies.

Make it a script so you never retype it:

{
    "scripts": {
        "build": "esbuild src/index.js --bundle --platform=node --format=cjs --external:express --external:node-fetch --outfile=server.cjs"
    },
    "devDependencies": { "esbuild": "^0.24.0" }
}
Commit the built file

NimoTavern installs straight from GitHub and doesn't build anything. If server.cjs is in your .gitignore, users get the error "manifest.json points to "server.cjs", but that file is not in the repository".

Before and after

// plugins/my-plugin/index.mjs
import fs from 'node:fs';
import path from 'node:path';
import yaml from 'yaml';

export const info = { id: 'my-plugin', name: 'My plugin', description: '…' };

export async function init(router) {
    const file = path.join(process.cwd(), 'plugins', 'my-plugin', 'presets.yaml');
    router.get('/presets', (req, res) => {
        res.json(yaml.parse(fs.readFileSync(file, 'utf8')));
    });
}
// src/index.js, built to server.cjs
import fs from 'node:fs';
import path from 'node:path';
import yaml from 'yaml';                 // bundled by esbuild

export const info = { id: 'my-plugin', name: 'My plugin', description: '…' };

// On NimoTavern, files you ship live in nimo.extensionDir.
const here = typeof nimo !== 'undefined'
    ? nimo.extensionDir
    : path.join(process.cwd(), 'plugins', 'my-plugin');

export async function init(router) {
    const file = path.join(here, 'presets.yaml');
    router.get('/presets', (req, res) => {
        res.json(yaml.parse(fs.readFileSync(file, 'utf8')));
    });
}
  • Only the path to the shipped file: process.cwd() means nothing in a browser, nimo.extensionDir is where your repository's files are.
  • typeof nimo !== 'undefined' tells you which one you're on, so one codebase serves both. The built server.cjs also runs as a regular SillyTavern plugin: copy it to SillyTavern's plugins/ folder.
  • The yaml package is bundled by esbuild. fs and path come from NimoFramework.

What your plugin can use

Modules you can require

These work with require() (with or without the node: prefix) and need no bundling:

ModuleHow it behaves here
expressRouter() with get/post/put/patch/delete/all/use, route parameters, and sub-routers. express.json() and friends exist but do nothing: bodies are already parsed (see below).
fs, fs/promisesThe user's own files, decrypted in their browser. Sync, callback and promise styles all work. Every write is encrypted and synced to the user's other devices.
pathPOSIX paths (/). Paths look like /data/default-user/….
node-fetchThe browser's fetch, plus the opt-in relay. See Calling other websites.
cryptorandomUUID, randomBytes, createHash and createHmac (sha1, sha256, sha512, md5). For anything heavier, use crypto.subtle (Web Crypto), which is available too.
buffer, events, stream, stream/promises, string_decoder, util, url, querystringStandard browser ports of the Node modules.
readlinecreateInterface({ input }) over a stream, to read lines ('line' events or for await).
assert, timers, timers/promises, perf_hooks, console, tty, os, processSmall versions. os.platform() is 'linux', process.env is empty, process.cwd() is '/srv', process.exit() throws.

Anything else: if it's a pure-JavaScript npm package, bundle it. If it needs native code or the operating system, see limits.

Requests and responses

You getDetails
req.bodyAlready parsed. JSON → object. multipart/form-data → its text fields. URL-encoded forms → object. Anything else arrives as a string: to send binary data, use multipart or base64 inside JSON.
req.fileThe first uploaded file of a multipart request, like multer gives you: { fieldname, originalname, mimetype, size, path }. Read it with fs.readFileSync(req.file.path).
req.query, req.params, req.headers, req.get(), req.method, req.pathAs in Express.
req.user.directoriesSillyTavern's folders for this user: characters, chats, worlds, extensions, backgrounds, files… Use these rather than hard-coded paths.
res.json(), send(), status(), sendStatus(), set(), type(), sendFile(), download(), redirect()As in Express.
res.write() + res.end()Streaming works: each write() reaches the page as it happens (good for AI-style streamed text).

Storing data

Everything your plugin writes, with nimo.storage or fs, is encrypted in the user's browser and saved like the rest of their tavern. It's on their other devices after a sync, and NimoTavern can't read it.

  • Settings and small state: nimo.storage. No paths to think about.
  • Files: fs in nimo.dataDir. Keep them reasonably small: each change is encrypted and uploaded.
  • Don't rely on memory. The browser stops the Service Worker when it's idle, and your plugin with it. Anything only in a variable is gone after that (see lifecycle).

Calling other websites

Your plugin calls websites from the user's browser, so the browser's rules apply: the site must allow cross-origin requests (CORS). Most AI providers do. When a site doesn't, the request fails with:

Request to api.example.com failed: Failed to fetch. This provider blocked a direct browser request (CORS). You can enable the optional NimoTavern relay in User Settings > NimoTavern Privacy.
  • If the user turned on the opt-in relay, fetch retries through it automatically. Check nimo.relay to adapt your UI or messages.
  • Requests carry no cookies (credentials: 'omit'). Pass API keys in headers, as you would from Node.
  • Addresses on the user's own network (localhost, 192.168.…) work if that service allows CORS. They're never sent to the relay.

Debugging

When the server part of an extension can't start, the rest of the extension still loads, and NimoTavern tells the user and you why:

  • A red toast names the extension and gives the reason, with a link to this section.
  • The browser console (F12 → Console) shows lines starting with [NimoFramework]: what loaded, at which URL, and every error with its stack. Your plugin's own console.log lines appear there too, tagged with your extension's folder name, like [my-extension] ….
  • /api/plugins/status lists loaded plugins with their routes, and the errors.

Answers your UI may see from /api/plugins/…:

  • 404 [NimoFramework] plugin "my-plugin" has no route for GET /x: check the path and method.

  • 404 Plugins are turned off on the multiplayer site.: expected on play.nimorp.lol.

Lifecycle

  • Start: plugins start on the first request to /api/plugins/ after the page opens, not before. Your UI's first call (often /probe) starts them.
  • init() can run many times. The browser stops an idle Service Worker (often after about 30 seconds without requests) and starts it again on the next one. Keep init quick and safe to repeat, and keep state in storage.
  • Restart: when an extension is updated, enabled, disabled or removed, all plugins restart on the next request. exit() is called first (it gets 5 seconds).
  • UI changes need a page reload, like on SillyTavern.

Updating and the dev loop

  1. Change, build, commit, push (npm run build, then commit server.cjs with your source).
  2. Update on NimoTavern: Extensions → Manage extensions → update your extension.
  3. Reload the page to load the new UI. The server part already restarted.
Test on a branch

Install your work-in-progress from a branch: https://github.com/you/my-extension/tree/dev. A sub folder works too: …/tree/main/extensions/my-extension. Users keep using the default branch.

Limits

Some things can't exist in a browser. Each one has a replacement that usually does the job:

Not availableUse instead
child_process, Python or other programsCall a web API with fetch, or do the work in JavaScript or WebAssembly.
http/https requestsfetch (or require('node-fetch')).
app.listen(), net, tls, dgram, a WebSocket serverYour routes are your server. For live updates, stream with res.write(). The browser's WebSocket client is available for connecting out.
sqlite3, better-sqlite3nimo.storage or files, or bundle sql.js (SQLite in WebAssembly).
sharp, canvasOffscreenCanvas and createImageBitmap, which are available here.
zlibBundle fflate or pako, or use the built-in CompressionStream.
worker_threads, cluster, vmKeep the work inside your route handler.
Timers and background jobsThe Service Worker sleeps when idle and your timers stop with it. Do the work when a request arrives.
process.envEmpty: users have no environment. Store settings with nimo.storage and let users edit them in your UI.
  • Multiplayer: no extension and no plugin ever runs on the multiplayer site (play.nimorp.lol). That's how NimoTavern guarantees other players' messages stay out of reach.
  • Install size: GitHub repositories up to 2,000 files and 30 MB (10 MB per file).
  • init() must finish within 20 seconds.

Checklist before publishing

  • manifest.json has "nimo": { "framework": 1, "server": "server.cjs" }.
  • server.cjs is committed and up to date (run the build before every release).
  • info.id is unique and made of lowercase letters, digits, - or _.
  • Your UI handles "backend not available" gracefully (the /probe check), for example on the multiplayer site.
  • No state lives only in memory.
  • You installed it from GitHub on NimoTavern, opened the console, and saw [NimoFramework] loaded "…".
  • Your README says it works on NimoTavern. Users look for that.

FAQ

Do users need to do anything special?

No. They install your extension from its GitHub address like any other. The server part loads on its own.

Can I keep one repository for SillyTavern and NimoTavern?

Yes. SillyTavern ignores the nimo manifest field, and the built server.cjs also works as a regular SillyTavern plugin. Branch on typeof nimo where behaviour differs (usually only file paths and storage). The example does exactly this.

Is my plugin's data private?

Yes, as private as the user's chats: encrypted in their browser with their key. NimoTavern stores it without being able to read it. Only that user, on their devices, can.

Can my plugin talk to my own server?

Yes, with fetch. Your server must send CORS headers allowing https://nimorp.lol (or *). Remember the request then leaves the user's browser: say so in your README.

Why CommonJS and not ES modules?

A plugin is loaded from the user's encrypted files, where browsers can't import modules directly. A single CommonJS file loads reliably and fast. esbuild does the conversion, so you can keep writing ES modules.

Something doesn't work and this page doesn't explain it

Open an issue on GitHub with the console lines starting with [NimoFramework] and your repository's address.
