The DEK is wiped from memory right after the two working keys are derived. The working keys are imported into the browser's WebCrypto as non-extractable keys: even code running in the page can use them to encrypt and decrypt, but can't read their raw bytes.

Login

  1. Ask for parameters. The browser sends only your username; the server returns your public salt and KDF settings. (For unknown usernames it returns a plausible fake salt, so you can't probe which accounts exist.)
  2. Derive. Argon2id turns your password into the KEK and the login proof.
  3. Prove. The browser sends the proof. The server checks it against its stored scrypt hash (constant time) and, if it matches, starts a session and returns your wrapped DEK.
  4. Unlock. The KEK opens the wrapped DEK locally. Working keys are derived and stored in the browser; the DEK is wiped.

Syncing

The server keeps a per-account increasing sequence number. Your browser remembers the last number it saw and asks "what changed since N?". The answer is a list of (id, size, seq) entries; the browser fetches new blobs in batches, decrypts them locally and merges. Deletions are recorded as tombstones. Files that are identical to SillyTavern's shared default content (like the built-in Seraphina card) are stored as references instead of copies.

Recovery and password changes

  • Forgot password: the phrase is stretched into a recovery key and recovery proof. The server verifies the proof and returns the second wrapped DEK. The browser opens it, wraps the DEK under a new password key, and generates a new recovery phrase (the old one is retired).
  • Change password: the DEK is re-wrapped under the new password key. Your data isn't re-encrypted, so it's instant, however big your tavern is.
  • New recovery phrase: a new recovery wrap replaces the old one. The old phrase stops working.
  • Log out everywhere: deletes all session records server-side. Each device's local keys are wiped when it next syncs or logs out.

Threat model

AttackerCan they read your data?
Passive network observerNo: TLS to Cloudflare and the data is already encrypted inside it.
Cloudflare (as the TLS endpoint)Sees ciphertext and metadata, not plaintext.
Curious or coerced operator with database accessNo: only ciphertext, hashes and salts.
Database leak, then offline password guessingPossible only for weak passwords; Argon2id makes each guess cost 64 MiB and real time.
Malicious operator shipping modified JavaScriptYes, in principle: the web delivery model. Mitigations: open source, reproducible build steps, strict CSP, you can inspect the running code.
Malware on your device / XSS in the pageCan use the working keys while you're logged in. Mitigated by CSP and non-extractable keys, but not eliminated.
Anyone with your recovery phraseYes: treat it like the master key it is.
